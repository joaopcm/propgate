# Register a domain

<EndpointHeader
  cliCommand="propgate domains add <domain> --profile <key> [--expect <requirement>.<field>=<value>]"
  method="POST"
  path="/v1/domains"
/>

A write, not a check. Registering a domain **does not touch DNS** — it starts
`pending` with no result, and stays that way until something calls
[verify](/api/domains/verify) on it. Registration and verification are
separate calls on purpose: importing ten thousand domains must not fire ten
thousand DNS runs as a side effect of a bulk insert.

`externalId` is your retry key: sending the same one again does not create a
second row, it returns the domain that already exists. `meta.created` is what
lets your retry logic tell "this is the customer I already had" from "this is
a new one" without keeping a mapping table of its own.

Because that branch writes nothing, it is **not** how you rotate a value. Sending
the same `externalId` with new `expectations` returns `200` having changed nothing,
and the sweeper keeps comparing the old value. Use
[update](/api/domains/update) instead.

Registering a name that already exists under a **different** external id is a
`409` — that would be two records of one domain, and quietly returning one of
them would hide it:

<CodeBlock code={REGISTER_NAME_TAKEN} lang="json" />

## Values the profile requires

If the profile names anything in `requiredPerDomain`, those values are part of
registering. Omit one and the call is refused, naming the path to set:

<CodeBlock code={REGISTER_MISSING_EXPECTATION} lang="json" />

A `422` here rather than a domain that registers and reports `indeterminate`
forever: the second one is only discoverable from a dashboard days later, and by
then it looks like a check that is failing rather than a value that never arrived.
See [Profiles and versions](/concepts/profiles) for why a DKIM key belongs on the
domain rather than in the profile.
