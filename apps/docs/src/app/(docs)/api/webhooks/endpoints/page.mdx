# Webhook endpoints

Seven routes under `/v1/webhooks`, documented on one page because they are
one resource rather than seven. This page is the CRUD surface — creating,
listing and configuring endpoints, rotating their secrets, and reading
delivery attempts. For the four events, the payload shape, and verifying a
signature, see [Webhooks](/webhooks); signatures are valid for
{TIMESTAMP_TOLERANCE_SECONDS} seconds, which this page does not repeat.

No CLI commands yet — webhooks are managed over the API only.

<Callout>
  None of the requests or responses on this page are captured — there is no
  webhooks section in QUICKSTART.md to quote from. Every one is a shape read
  off `apps/api/src/routes/webhooks.ts`: its zod schemas for the requests, and
  its `serialise` function (or, for rotation and deliveries, the object the
  route builds itself) for the responses.
</Callout>

Creating is idempotent on `(account, url)` — posting the same URL again
returns the existing endpoint rather than a second one, and `meta.created`
tells the two apart. `secret` is only ever present in **this** response: on a
retry that matched an existing endpoint, the stored secret is not this call's
to hand back, since it exists to sign with, not to be read.

A URL that fails the `https`-and-not-private check is a `422`:

## Rotate the secret

<EndpointHeader method="POST" path="/v1/webhooks/:id/secret" />

`POST /:id/secret` rather than `/:id/rotate-secret`: this call *creates* a
secret, so the noun in the path is the resource and `POST` is the verb. Once a
family has one route spelling the verb in the path and another that doesn't,
which one a given action gets stops being predictable.

<ParamsTable
  rows={[

## Deliveries

<EndpointHeader method="GET" path="/v1/webhooks/:id/deliveries" />

Nested under the endpoint rather than listed account-wide, for two reasons.
First, a delivery belongs to exactly one endpoint, and "did *this* endpoint
receive it" is the question this call answers — an account-wide list would
answer a different one. Second, an account-wide `/v1/webhooks/deliveries`
would collide with `/v1/webhooks/:id` in the route table, and which one wins
would depend on declaration order rather than on anything the URL says.

<ParamsTable
  rows={[

    { description: "From a previous page's meta.nextCursor.", name: "cursor", type: "string" },

  ]}

<CodeBlock code={DELIVERIES_CURL} lang="bash" />
<CodeBlock code={DELIVERIES_RESPONSE} lang="json" />

`lastError` is what makes a dead-lettered delivery answerable — null while
pending and after an eventual success, and the transport error otherwise.
`payload` is the same body that was sent, byte for byte, so a delivery that
failed can be replayed by hand without recomputing it. See
[Webhooks](/webhooks#retries) for the retry schedule and which status codes
trigger one.
