# Create a profile

<EndpointHeader method="POST" path="/v1/profiles" />

A profile is what you expect of a domain's records: a named list of
requirements, each with a key you choose. Results are reported against those
keys, so pick ones you can switch on.

## Editing writes a new version

Posting the same `key` again never changes this version — it writes the next
one, and every domain already registered against `sending` stays pinned to
whichever version it was registered against. Full reasoning, and what "pinned"
means for a domain mid-flight, is at
[Profiles and versions](/concepts/profiles).

## Rejected at write time

A definition is refused before it is ever stored if a requirement inside it
could never be answered:

- no requirements, or more than 20
- a duplicate requirement key
- a `dkim` requirement with neither a `selector` nor `selector` in
  `requiredPerDomain`, or two `dkim` requirements sharing one literal `selector`
- a `caa` requirement with neither a `caaIssuer` nor `caaIssuer` in
  `requiredPerDomain`
- a `requiredPerDomain` naming a field the check kind never reads — a value you
  would supply forever and nothing would ever compare
- a field that is both set here and named in `requiredPerDomain`, because there
  is no rule for which one wins
- two requirements naming the same non-`dkim` check — `dkim` is the one check
  that answers a question per selector rather than per domain, so it is the
  one allowed to repeat

Two `dkim` requirements that both defer `selector` are accepted: their values are
not known until a domain supplies them, so uniqueness is not decidable here. If
they resolve to the same selector it is evaluated twice and both requirements are
attributed the same outcome — wasteful, not wrong.

Accepting a definition like this and failing later, once a customer already
relies on it, would be a promise this API took and could not keep. A `422` at
write time is the same finding delivered while it is still cheap to fix.
