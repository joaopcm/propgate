# Profiles and versions

A profile is what a tenant expects of a domain's records: a named list of
requirements, each with a key you choose. Registering a domain does not point
at "the sending profile" in the abstract. It pins the specific version that
existed at that moment.

## Editing writes a new version

Posting the same `key` again does not change version 1. It writes version 2
and leaves the first row exactly as it was:

<CodeBlock code={PROFILE_EDIT_CURL} lang="bash" />
<CodeBlock code={PROFILE_EDIT_RESPONSE} lang="json" />

Every domain already registered against `sending` stays pinned to whichever
version it was registered against. Version 2 changes what a *new*
registration means, not what an existing domain is judged by.

This is not a caution about a hypothetical. Webhooks fire on every state
transition, so an edit that reclassified every domain on a profile at once
would land as a storm in every one of your customers' inboxes, with no deploy
on your side to explain it. Pinning the version is what keeps "we tightened
our sending profile" from turning into "we tightened it and every customer got
paged."

## The profile is the shape; the domain is the values

A DKIM key is issued per domain. The key for `acme.com` is not the key for
`globex.com`, so a field holding one cannot live on a template that ten thousand
domains share — that would be ten thousand profiles, and the versioning above
would stop meaning anything.

So a requirement names the fields it takes from the domain instead of setting
them here:

<CodeBlock code={PROFILE_PER_DOMAIN_CURL} lang="bash" />

and each domain supplies them at registration:

<CodeBlock code={DOMAIN_EXPECTATIONS_CURL} lang="bash" />

The `include` stays in the profile because `_spf.google.com` is the same for
every domain you send for. The key does not, because it is not. That is the whole
rule: what is true of your platform belongs in the profile, and what you issue per
customer belongs on the domain.

Four fields can be deferred — `expectedPublicKey`, `selector`, `include` and
`caaIssuer`. `expectsMail` deliberately cannot: it asserts what a domain is *for*,
which is exactly what a profile is.

Supplying `expectedPublicKey` is what turns "a valid key is published here" into
"*your* key is published here" — the difference between passing a domain that
pasted a competitor's record and catching it.

### A required value that is missing is never a pass

Omit one and the registration is refused, naming the path to set:

<CodeBlock code={DOMAIN_EXPECTATIONS_MISSING} lang="json" />

If a domain somehow reaches a check without one, every requirement comes back
`indeterminate` with an `EXPECTATION_MISSING` finding, and no DNS is sent at all.
It never reads as `pass`. This matters more than it looks: a valid DKIM key
probably *is* published at that selector, so a check that forgot the expectation
would find one and report success.

### Rotating a value

`PATCH /v1/domains/:id` replaces a domain's values, re-points it at another
profile, or both. The domain returns to `pending` and **no webhook fires** — the
compared value moved because you moved it, and a `domain.failed` across a fleet
mid-rotation would page every one of your customers for nothing. Nothing is
appended to that domain's timeline for the first check afterwards either, for the
same reason: it would claim the customer's zone changed when it did not.

For zero-downtime rotation, add a **second selector** in a new profile version and
`PATCH` the domain onto it rather than swapping the value in place. Both keys are
legitimately correct while DNS catches up, and several `dkim` requirements per
profile is what the one repeatable requirement type is for.

One thing this does not stop: a new profile version that *drops* a
`requiredPerDomain` declaration without setting a literal is accepted, and quietly
weakens "your key is published" back to "a key is published". It is your profile,
so it is your call — but it is a weakening you will not be warned about.

## Rejected at write time

A definition is refused before it is ever stored if a requirement inside it
could never be answered: a duplicate key, two requirements competing for one
check, a DKIM requirement with neither a selector nor one required per domain, a
CAA requirement with no issuer from either side. The same applies to a field that
is both set in the profile and required per domain — there is no rule for which
would win, so the write is refused rather than resolved by convention.

<CodeBlock code={PROFILE_REJECTED_CURL} lang="bash" />
<CodeBlock code={PROFILE_REJECTED_RESPONSE} lang="json" />

Accepting a definition like this and failing later, at read time once a
customer is already relying on it, would be a promise the API took and could
not keep. A `422` at write time is the same finding delivered while it is
still cheap to fix.

Six exist, rendered here straight from the same table the API reference and
the tests read, so this list cannot say something the resolver cannot
actually check.
