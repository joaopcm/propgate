# domains

Seven commands over the seven `/v1/domains` endpoints. Each is a thin client —
the cURL beside a command issues the identical request, so the two references
agree on the shape.

## `domains add --profile`

Registration is a write, not a verification. It does not touch DNS.

<CodeTabs
  items={[
    { code: ADD_CURL, label: "cURL", lang: "bash" },
    { code: ADD_CLI, label: "CLI", lang: "bash" },
  ]}
/>
<CodeBlock code={ADD_OUTPUT} lang="text" />

`--profile` is required — a domain that names no profile has nothing to be
checked against, so the API refuses it with a `422` rather than accepting a
domain with no meaning. Nothing has been checked yet: `state: pending` here
means "nobody has looked", not "broken". The sweeper picks up the first check
on its own schedule.

## `--expect` for values the profile requires per domain

If the profile names anything in `requiredPerDomain` — a DKIM key it issued for
this domain, say — pass it with `--expect <requirement>.<field>=<value>`, once per
value:

<CodeTabs
  items={[
    { code: ADD_EXPECT_CURL, label: "cURL", lang: "bash" },
    { code: ADD_EXPECT_CLI, label: "CLI", lang: "bash" },
  ]}
/>

Without these the API refuses the registration, naming the path it wanted. The
value is split on the **first** `=`, so a base64 key keeps its `=` padding, and the
requirement key is everything before the **last** `.`. Giving the same
`<requirement>.<field>` twice is an error rather than a last-one-wins: a typo and a
genuine second value look identical here, and silently dropping one of two keys is
how a domain ends up verified against the wrong one.

See [Profiles and versions](/concepts/profiles) for why a key belongs on the domain
rather than in the profile.

## `domains update` for rotating one

<CodeTabs
  items={[
    { code: UPDATE_CURL, label: "cURL", lang: "bash" },
    { code: UPDATE_CLI, label: "CLI", lang: "bash" },
  ]}
/>
<CodeBlock code={UPDATE_OUTPUT} lang="text" />

`--expect` replaces the whole set, so send every value the profile requires and
not only the one that moved. `--profile <key>` re-points the domain at another
profile instead, and the two can be combined. One of them is required — a call
that changes nothing would still reset the domain and re-verify it, so the CLI
refuses it rather than making that a silent side effect.

The domain goes back to `pending` and **no webhook fires**. The value being
compared changed because you changed it, not because your customer's DNS moved,
and a `domain.failed` across a fleet mid-rotation would page every one of your
customers for nothing.

Re-sending `domains add` with the same `--external-id` does **not** rotate
anything: that path is idempotent by design and answers `200` having written
nothing. Rotation is this command.

`--state` filters to one of the five states `domain_state` defines: `pending`,
`verifying`, `verified`, `degraded`, or `failed`. Omit it to list everything.
An empty result prints its own line rather than nothing at all — a blank
terminal after a real command looks like a failure:

`--external-id` filters to the domain carrying one of your own ids.

### Paging

<CodeBlock code={LIST_PAGED} lang="bash" />

The endpoint is cursor-paged: `meta.nextCursor` names where the next page
starts, and `--all` follows it to the end. `--all` asks for the server's
maximum page size of 200, so a full walk is one round trip per 200 rows rather
than per 50. It is refused alongside `--cursor`, which says where to start —
picking one silently would be guessing at which you meant.

Domains sort ascending by id, so a domain registered while a walk is in
progress lands at the end and is included. (Deliveries sort the other way and
miss them; the asymmetry is the endpoints', not the CLI's.)

## `domains get`

<CodeBlock code={GET_OUTPUT} lang="text" />

The per-requirement breakdown, which is the thing `domains list` has no room
for. Read `satisfied` — the `ok`/`x` column — rather than the verdict alone: a

## `domains check`

<CodeBlock code={CHECK_CLI} lang="bash" />

Runs every check the domain's profile names **and writes the result**. This is
not the same command as [`propgate check`](/cli/check):

| | reads DNS | writes state | can fire a webhook | needs a key |
|---|---|---|---|---|
| `propgate check <domain>` | yes | no | no | no |
| `propgate domains check <id>` | yes | yes | yes | yes |

<Callout>
  Because those differ in what they *do* rather than only in what they take,
  `propgate check` refuses a uuid rather than routing it:

  <CodeBlock code={REDIRECT} lang="text" />

  Nothing goes over the wire. Reaching a state-writing, webhook-firing call by
  typing the wrong shape at the wrong verb is the outcome this declines.
</Callout>

Rate limited to 100 checks a minute per account, separately from the general
request limit. Continuous re-checking is the sweeper's job and does not come
through here.

## `domains timeline`

<CodeBlock code={TIMELINE_CLI} lang="bash" />
<CodeBlock code={TIMELINE_OUTPUT} lang="text" />

What actually changed, newest first. Nothing is appended for a check that
found the same values as last time — which is why an empty timeline says so
rather than printing nothing:

<CodeBlock code={TIMELINE_EMPTY} lang="text" />

"Nothing has changed" and "nothing has happened" are different statements, and
only the first is true of a domain checked hourly for a month and never
altered. `--limit` bounds the rows, up to 200; this endpoint has no cursor.
