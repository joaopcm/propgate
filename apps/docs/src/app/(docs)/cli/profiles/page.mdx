# profiles

A profile is an array of up to twenty objects with six possible fields each,
which is more structure than a flag naturally carries. There are three ways
to give it, and they exist for three different callers.

## `--require`, for a one-liner

  items={[

    { code: CREATE_CLI, label: "CLI", lang: "bash" },
  ]}
/>
<CodeBlock code={CREATE_OUTPUT} lang="text" />

Each `--require` is `<key>:<check>[:field=value,field=value]`, repeatable up
to the twenty the API allows.

The field names are **the API's own body field names, verbatim**. Not
`--dkim-selector` but `selector`; not `--spf-include` but `include`. That is
deliberate: when the server refuses a definition it names the field, and an
alias here would mean the error and the input never quite match.

| Check | Fields |
|---|---|
| `delegation` | none |
| `spf` | `include` |
| `dkim` | `selector` (required), `expectedPublicKey` |
| `dmarc` | none |
| `mx` | `expectsMail` |
| `caa` | `caaIssuer` (required) |

Plus `requiredPerDomain` on any of them — see below.

Values keep everything after the first `=`, so a base64 key retains its
padding — a DKIM key that quietly lost its `==` is one that never matches for
a reason nobody can see.

## Deferring a value to each domain

A DKIM key is usually issued per domain, so pinning one in the profile would
mean a profile per customer. `requiredPerDomain` names the fields the *domain*
supplies instead, and each domain then passes them with
[`domains add --expect`](/cli/domains).

<CodeBlock code={PER_DOMAIN_CLI} lang="bash" />
<CodeBlock code={PER_DOMAIN_OUTPUT} lang="text" />

It is the one field where **repeating an assignment accumulates** rather than
overwrites, because it is the one field that holds a list. Everything else in
the micro-syntax is a single value.

`profiles get` prints deferred fields as `per domain: …` rather than omitting
them. The difference between a profile that stands on its own and one every
domain must supply a value for is the whole reason a later registration fails,
and that `422` names the field without naming the profile that asked for it.

### What is checked here, and what is not

Two rules are enforced before anything is sent: **`dkim` needs a selector**
and **`caa` needs an issuer** — from one side or the other. Naming the field in
`requiredPerDomain` satisfies the rule, because the value arrives with the
domain instead.

<CodeBlock code={REJECTED} lang="text" />

Those two are not a second copy of the server's validation — they are the two
that decide which question the guided flow asks next, so this code needs them
anyway. Everything else about a valid profile stays on the server: duplicate
keys, more than twenty requirements, two of a kind that may only appear once.
A second implementation of a rule is a second thing that can disagree, and the
API's `422` is already the better message.

## `--file`, for something generated

<CodeBlock code={FILE_CLI} lang="bash" />

Takes the `POST /v1/profiles` body exactly — `{ "key": …, "requirements": […] }`
— and `-` reads stdin. It carries the key too, so it is refused alongside
`--key` and `--require` rather than leaving a reader to guess which wins.

## No flags at all, for a person

<CodeBlock code={GUIDED} lang="text" />

One requirement at a time, asking only the fields that check actually has —
including whether a value is the same for every domain or issued per domain.
`mx` offers three answers rather than a yes/no, because `expectsMail` is
tri-state: unstated makes no claim, and `false` asserts the domain receives no
mail — which makes a null MX correct rather than a fault.

## `profiles get`

<CodeBlock code={GET_CLI} lang="bash" />

Returns the **current** version — the one a new registration against this key
would pin to. Domains already registered keep their own version regardless.
See [Profiles and versions](/concepts/profiles).
