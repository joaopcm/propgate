# accounts

`signup`, `confirm`, and `keys` are the commands that talk to
[api.propgate.dev](https://api.propgate.dev) — the half of the CLI that
`check` does not touch. Every example below shows the cURL a script would use
alongside the CLI command that does the same thing.

## Getting a key

Two calls. The first sends a six-digit code to the address you give it; the
second exchanges that code for a key.

<Callout>
  `confirm` prints the key once and stores it in
  `$XDG_CONFIG_HOME/propgate/config.json` at mode `0600`. Only a hash is kept
  on the API side — there is no endpoint that can show the plaintext again.
  Running the flow a second time on the same address mints an *additional*
  key rather than a second account, which doubles as the recovery path for a
  lost key.
</Callout>

<CodeTabs
  items={[
    { code: REVOKE_CURL, label: "cURL", lang: "bash" },
    { code: REVOKE_CLI, label: "CLI", lang: "bash" },
  ]}
/>
<CodeBlock code={REVOKE_OUTPUT} lang="text" />

<Callout>
  `keys revoke` takes a **prefix**, not an id — the prefix is the part of a
  key still readable after it was issued, since only a hash of the rest is
  ever stored. The API route itself takes an id, deliberately: a
  four-character prefix carries no unique index, so the CLI lists your keys
  and resolves the prefix on your side of the request, where an ambiguous
  match can be reported rather than guessed.
</Callout>

<CodeBlock code={REVOKE_AMBIGUOUS} lang="text" />

If a prefix matches more than one key, the command refuses and prints every
id it matched instead of picking one.

Read-only, and there is no `members add`. Membership is granted by proving
control of a mailbox through `signup`, so a command that added someone would
be a command that added someone who proved nothing.
