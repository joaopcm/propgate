# CLI

`@propgate/cli` is the same engine as the public checker and the API, run
from a terminal. `propgate check` is what you reach for when a customer
reports something odd, because it runs against whichever resolver *they* are
using rather than against ours.

Published as `@propgate/cli`, MIT licensed, built on
[`@propgate/dns`](https://www.npmjs.com/package/@propgate/dns), which has zero
runtime dependencies of its own — that claim is about the resolver, and it is
the one that matters. The CLI adds `@clack/prompts` for the guided flow below,
loaded only when there is a person to prompt: `propgate check` never reaches
it. `propgate --version` prints the version out of `package.json` rather than a
constant baked in at build time, so it never drifts from what was actually
published. Requires Node 20 or later.

## The split that matters

The CLI has two halves, and they do not touch:

- **`propgate check`** needs no account, no config file, and no network
  beyond DNS. It resolves against whichever server you point it at — the
  system resolver by default — and never talks to propgate's API. A machine
  that has never run `signup` loses nothing.
- **Everything else** — `signup`, `confirm`, `keys`, `members`, `profiles`,
  `domains`, `webhooks` — is a client of
  [api.propgate.dev](https://api.propgate.dev). These are the commands that
  need a key.

`propgate check --remote` is the seam between the two: same command, same
output, but the question goes to our API instead of to your resolver.

Every endpoint the API has is reachable from here — a spec in the package
asserts it both ways, so a route without a command fails a test rather than
going unnoticed.

See [`check`](/cli/check) for the diagnostic half, and
[`accounts`](/cli/accounts), [`profiles`](/cli/profiles),
[`domains`](/cli/domains) and [`webhooks`](/cli/webhooks) for the half that
manages a tenant.

## Two ways to run anything

Every command takes its arguments as flags. Leave a required one out and, if
there is a terminal to ask in, it asks:

That is the same declaration behind both paths — one list of fields per
command generates the flag and the question — so the two cannot describe
different arguments.

When there is nobody to ask, it does not wait. **A CLI that blocks on stdin
because a flag was missing is worse than one that errors**: it hangs a build
until the runner's timeout with nothing on stderr saying why. So it names
every missing flag at once and exits `64`:

<CodeBlock code={NON_INTERACTIVE} lang="text" />

Prompting is off whenever any of these is true, and each is checked because
the others miss a real case:

| Condition | Why |
|---|---|
| stdin or stdout is not a TTY | The usual pipe or redirect |
| `--json` was passed | Asking for machine-readable output says nobody is reading |
| `CI=true` | Some runners allocate a pty, so the TTY check alone is not enough |
| `PROPGATE_NO_INPUT=1` | A wrapper script started from an interactive shell |

## The config file

`confirm` is the only command that writes to disk. It stores the key it
receives at:

<CodeBlock code={CONFIG_PATH} lang="text" />

`$XDG_CONFIG_HOME` when it is set to an absolute path, `~/.config` otherwise.
The file is written mode `0600` — via a temporary file with that mode,
renamed over the target, rather than written in place and `chmod`ed after, so
the key is never briefly world-readable on a shared machine.
